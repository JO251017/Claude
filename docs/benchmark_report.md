## 1. 핵심 결론

1. **가장 참고할 플랫폼 3곳: DSers, Nextflow, 플레이오토**
   - **DSers**: "공급처 매핑 → 재고·가격 동기화 규칙 → 알림 → 일괄 발주 → 송장 동기화" 구조가 공개 문서로 가장 잘 정리되어 있고, 무료 플랜이 있어 직접 써 볼 수 있다.
   - **Nextflow**: 국내 스마트스토어 + 위탁 공급처를 대상으로 같은 문제(발주·송장)를 푼다. 특히 **API가 없는 공급처를 메일·엑셀로 처리**하는 방식과 처리 이력·재처리 구조가 국내 현실에 맞다.
   - **플레이오토**: 국내 통합관리(OMS) 요금의 기준점이다. LIGHT가 "무재고 판매 특화"로 월 5만 원이라 "직접 개발 vs 구매" 판단 기준이 된다.
2. **지금 만든 0~1단계(키워드 발굴·순이익 판정)는 아이템스카우트·판다랭크의 핵심 기능과 겹치는 영역**이다. 차별점은 **원가·수수료·보수 시나리오까지 넣은 판정과 승인 기록**이다. 공식 수수료로 검증한 결과 판매수수료 설정이 공식과 달라 바로잡았다(3.003% → 3%).
3. **다음 단계(발주·송장)는 기술적으로 가능**하다. 네이버 커머스 API에 주문 조회·발주 확인·발송 처리·취소·반품·교환이 있고, 판매자 본인이 쓸 수 있다. 도매꾹은 승인 후 발주 API를 쓸 수 있다. 오너클랜의 주문·송장 API는 확인 필요다.
4. **그러나 월 30건 규모에서는 발주·송장 자동화의 경제성이 낮다** [추정]. Nextflow 월 4만 원은 최저시급 약 3.9시간분이다. 직접 개발에는 수십 시간이 든다. **먼저 실제 판매로 0~1단계 결과를 검증**하고, 주문이 늘면 그때 만들거나 사는 것이 맞다.

## 5. 국내 적용 가능성

### 5-1. 해외 시스템의 작동 순서 (DSers·AutoDS 공통) [사실 + 정리]
1. 공급처 상품 가져오기 → 2. 스토어에 등록 → 3. **옵션 단위 매핑** → 4. 가격·재고 감시(DSers 하루 1회, AutoDS 상시) → 5. 규칙대로 반영(품절이면 재고 0, 임시저장, 게시 중단) + 알림 → 6. 주문 발생 → 매핑으로 공급처 상품 찾기 → 7. 공급처에 발주(일괄 또는 자동, AutoDS는 충전 잔액으로 결제) → 8. 송장 받아 스토어에 동기화 → 9. 오류(매핑 실패, SKU 변경, 품절)가 나면 자동 처리를 멈추고 알림

### 5-2. 국내 스마트스토어 쪽 조건 (1순위 조사 결과)
**네이버 커머스 API** [사실]
- 사용 조건: 스마트스토어 **통합 매니저 권한**이 있는 판매자가 커머스API센터에 가입하고 "내 스토어 애플리케이션"을 등록하면 쓸 수 있다(스토어당 최대 3개). 비정상 호출이 있으면 비활성 처리될 수 있다.
- 인증: OAuth2 Client Credentials. client_id와 timestamp를 bcrypt로 전자서명한 뒤 토큰을 받는다.
- 호출 제한: API별·애플리케이션별 초당 요청 수(토큰 버킷)이고, 초과하면 429(`GW.RATE_LIMIT`)가 온다. 구체 수치는 공개되지 않았고 응답 헤더로 알려 준다.
- 기능 분류(①~④):

| 기능 | 판정 | 근거(공식 API 목록) |
|---|---|---|
| 상품 등록·수정 | ① | 상품 등록/수정, 원상품 수정, 일괄 수정 |
| 가격 변경 | ① | 원상품·옵션 수정, 일괄 수정 (세부 항목은 확인 필요) |
| 재고 변경 | ① | 옵션 수정 (세부 항목은 확인 필요) |
| 주문 조회 | ① | 변경 상품주문 조회, 상품주문 상세 조회 |
| 발주 확인·발송 처리 | ① | 발주 확인, 발송 처리, 발송 기한 연장 |
| 송장 등록 | ① | 발송 처리(택배사·송장) |
| 취소·반품·교환 | ① | 취소 승인, 반품 승인·보류·거부, 교환 재배송 등 |

| 공급처 발주 | ② | 공급처 쪽 연동 필요 |

**공급처** [사실]

| 공급처 | 상품·가격 | 재고·품절 | 자동 발주 | 송장 | 연동 방식 |
|---|---|---|---|---|---|

### 5-3. 질문별 답
1. **작동 순서**: 5-1과 같다.
2. **공급처 ↔ 판매 상품 연결**: 옵션 단위 매핑표. 국내에서도 같은 구조를 쓰면 된다(스마트스토어 옵션 ↔ 도매꾹 상품번호·옵션코드).
3. **가격·재고 변동**: 해외는 자동 반영이 기본이다. 국내에서는 커머스 API로 반영할 수는 있지만, **잘못 바꾸면 바로 손실**이 나므로 우리 원칙대로 "알림 → 승인 → 반영"으로 둔다.
4. **주문 → 발주**: 주문 조회 → 발주 확인 → 매핑으로 공급처 상품 찾기 → (도매꾹) 주문서 생성 API 또는 (기타) 공급처 양식 엑셀·메일 → 송장 회수 → 발송 처리.
5. **오류 처리**: 매핑 실패, SKU 변경, 품절, 잔액 부족은 해당 건을 멈추고 사유를 기록하고 알린다. 나머지 건은 계속 처리한다(Nextflow·DSers 공통 방식이며, 우리 프로그램의 '항목 보류' 원칙과 같다).
6. **국내에 그대로 쓸 수 있는 것**: 옵션 매핑표, 품절·가격 변동 규칙과 알림, 일괄 발주, 송장 일괄 반영, 처리 이력과 재처리.
7. **국내에서 따로 개발해야 하는 것**:
   - 공급처마다 다른 연동 방식(도매꾹 API / 오너클랜 확인 필요 / 그 외는 메일·엑셀)
   - 국내 옵션 체계 매핑
   - 커머스 API의 bcrypt 서명 인증과 토큰 재발급
   - 상품정보제공고시·KC 인증 같은 등록 요건
   - **소비자 개인정보(주소·연락처)를 공급처에 넘길 때의 처리 기준** [추정: 법적 검토 필요]
   - 도매꾹 e-money 잔액 확인

### 5-4. 정책·데이터 제약 (H)
- 중복 상품 등록 제한, 어뷰징 페널티: 블로그 자료만 있음 [2차]. 네이버 운영정책 원문은 **확인 필요**.
- KC 인증·상품정보제공고시: 위탁 판매자의 책임 범위는 **확인 필요**(법령 원문 검토 필요). 커머스 API에 상품정보제공고시 조회 API가 있으므로 등록 시 입력은 필수로 보인다 [추정].
- 네이버 API 데이터를 AI에 넣어도 되는지: 커머스 API 'AI 활용 가이드'는 문서를 AI로 읽는 방법만 다룬다. 데이터 이용 조건은 **확인 필요**. 인증 정보를 AI에 넣지 말라고 명시되어 있다 [사실].
- 출처: https://apicenter.commerce.naver.com/docs/restriction , https://apicenter.commerce.naver.com/docs/ai-use-guide , https://notice.naver.com/notices/cac/16928 , https://notice.naver.com/notices/cac/16929

## 8. 최종 추천

1. **가장 먼저 상세 분석할 플랫폼: DSers**(무료 플랜으로 직접 써 볼 수 있음)
   - 매핑·동기화 규칙·알림·실패 처리가 공식 문서로 가장 잘 공개되어 있다. 무료로 직접 써 보며 화면과 규칙을 그대로 참고할 수 있다.
   - 스마트스토어는 지원하지 않으므로 **구조만** 가져온다.
2. **함께 볼 플랫폼: Nextflow**
   - 국내 스마트스토어 기준으로 같은 문제를 풀고 있다. 메일·엑셀 발주, 처리 이력처럼 국내 공급처 현실에 맞는 해법이 있다.
   - 주문이 늘었을 때 **직접 개발 대신 구매할 1순위 후보**이기도 하다(월 4만 원).
3. **지금 직접 개발을 이어 갈 범위**: 0~1단계(상품 선정 정확도)까지.
   - 이 부분은 상용 도구에도 "원가·수수료·보수 시나리오 판정 + 승인 기록"이 없어, 직접 만든 가치가 가장 크다.
   - 발주·송장은 판매가 검증된 뒤로 미룬다.
