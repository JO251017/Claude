# 스마트스토어 위탁판매 반자동 시스템 조사 프롬프트 v2

> v1 대비 바뀐 점은 문서 맨 끝 "변경 이력"에 있음. `{ }` 칸은 실행 전에 채운다.

## 역할
너는 이커머스 자동화 전문 시장조사 분석가이자 시스템 설계 컨설턴트다.
목표는 네이버 스마트스토어 위탁판매에 AI와 자동화를 적용해, **최소 비용으로 실제 작동하고 수익성을 검증할 수 있는 반자동 판매 시스템**의 다음 개발 방향을 정하는 것이다.
서비스를 나열하지 말고, 공식 문서·요금표·실제 운영 사례로 검증하라.

## 1. 프로젝트 배경
- 판매 채널: 네이버 스마트스토어 / 판매 방식: 위탁판매
- 개발자: 개인 1명, 주당 5~8시간, 개인 PC, Python·pandas·SQLite
- 비용 원칙: 초기 비용·월 유지비 최소화, 유료 API·유료 서비스는 원칙적으로 사용 안 함
- 운영 원칙: AI는 분석·추천, 프로그램은 계산·실행, 금전 손실 가능 작업은 사람 승인
- **운영 규모(비용 비교의 기준)**: 목표 상품 수 {예: 50개}, 예상 월 주문 {예: 30건}, 사용 중이거나 검토 중인 공급처 {예: 도매꾹, 오너클랜}
- **사람 시간 가치**: 시간당 {예: 10,000원} — 직접 개발 vs 솔루션 비교에 사용

## 3. 조사 항목 (우선순위 순)
분량이 크면 **1순위부터** 깊게 하고, 3순위는 요약만 해도 된다.

### 1순위: 다음에 만들 기능(M3~M5)의 가능 여부
**C. 네이버 커머스 API** — 최신 공식 문서만 사실로 인정
- 상품 등록·수정, 가격 변경, 재고 변경, 주문 조회, 발주 확인·발송 처리, 송장 등록, 취소·반품·교환
- 인증 방식, 사용 신청 조건(개인 판매자가 직접 쓸 수 있는지, 솔루션 등록이 필요한지), 호출 제한, 테스트 환경 유무
- 각 기능 분류: ① 공식 API로 가능 ② 외부 연동 필요 ③ 확인 필요 ④ 공식 API만으로는 어려움

**D. 공급처 연동** — {공급처 목록}을 우선, 이후 국내 주요 위탁 공급처
- 공식 API 여부, 상품·가격·재고 데이터 제공 방식(API/엑셀/피드), 자동 발주, 송장 제공, 이용약관상 자동화 허용 여부, 무료 여부
- 공식 연동과 비공식 크롤링을 구분. **공식 방식이 없으면 자동화 가능하다고 단정하지 말 것**

**H. 정책·법규 제약 (신규)**
- 스마트스토어 운영정책 중 자동 등록·대량 등록·중복 상품·가격 자동 변경 관련 제한
- 위탁판매 시 상품정보제공고시, KC 인증 등 등록 전에 확인해야 할 법적 요건
- 네이버 API로 받은 데이터를 **저장하거나 AI에 넣어도 되는지**(데이터랩·검색광고·쇼핑 검색·커머스 API 약관별)

### 2순위: 지금 만든 기능의 검증
**F. 수익성 데이터** — 위 "현재 설정값"이 2026년 실제와 맞는지 확인
- 스마트스토어 수수료 체계(판매·결제·유입 경로별), 광고비 수준, 카테고리별 반품률 자료 유무
- 데이터별: 무료 확보 가능 여부, 공식 API, 구매 필요 여부, 수집 주기, 신뢰도, 못 구할 때 대안
- 공급처 재고·공급가 변동, 반품·취소 위험을 무료로 얻을 방법
- **AI의 주관적 평가와 결정론적 계산을 구분**하고, 계산은 프로그램으로 처리하는 방식을 우선

**G. AI 쇼핑 에이전트 노출 (신규)**
- 네이버 쇼핑 AI 에이전트·AI 브리핑이 상품을 추천할 때 쓰는 정보에 대한 **네이버 공식 판매자 안내**가 있는지
- 없으면 "공식 안내 없음"으로 표시하고 보도·발표 자료만 출처와 함께 정리

### 3순위: 비교 정보
**A. 시장 현황** — 2026년 위탁판매 자동화가 실제로 쓰이는 방식(9개 업무: 솔루션, 상품 발굴, 상품명·상세페이지, 등록·수정, 가격·재고 동기화, 주문·발주, 송장, 고객 문의, 멀티채널)
- 업무별로 상용 서비스 기능 / 공식 API로 개발 가능 / 별도 개발 필요 / 기술·정책상 어려움 구분
- "AI 사용"을 홍보만 하는 서비스와 실제로 업무를 자동화하는 서비스를 구분

**B. 서비스 비교** — 서비스명·공식 홈페이지, 주요 기능, 판매 채널, 공급처, AI 기능과 일반 자동화의 차이, 무료 여부, 요금제·추가 비용, API 제공, 제약, 개인 판매자 적합성. 확인 못 한 가격·기능은 "확인 불가"

**E. 무료 AI** — ChatGPT·Gemini·Claude 무료 버전, 로컬 오픈소스 모델
- 업무 8개(시장 동향, 후보 추천, 상품명, 상세페이지 초안, 문의 분류, 응대 문안, 판매 분석, 위험 요인)별 적합 도구와 한계
- **무료 웹 서비스를 사람이 쓰는 것**과 **API를 프로그램에 연결하는 것**을 반드시 구분하고, API의 무료 한도·유료 전환 조건을 따로 확인
- H에서 확인한 데이터 제약 때문에 AI에 넣을 수 없는 데이터를 표시

## 4. 설계 (현재 구현에 이어서)
모듈: M0 시장·기회 탐색 / M1 후보 발굴 / M2 공급처·수익성 / M3 상품 등록 / M4 가격·재고 동기화 / M5 주문·발주 / M6 문의·사후 관리
- 각 모듈: 목적, 입력, 처리, 출력, 적용 AI, 일반 자동화 기술, 필요 API, 난이도, 비용, 예상 오류, 승인 필요 여부, 우선순위
- **M1·M2는 "이미 구현됨"으로 두고 보완점만** 제시. M3 이후는 1순위 조사 결과로 가능 여부부터 판정
- 앞 단계가 실제 데이터로 검증된 뒤에만 다음 단계로 간다

## 5. 반자동 운영 원칙
- AI는 분석·추천, Python은 계산·데이터 처리, SQLite는 저장, 공식 API는 외부 연동
- 상품 등록·가격 변경·발주처럼 금전 손실이 날 수 있는 작업은 사람 승인
- **오류 처리 구분**: 구조 오류(키 누락, 파일 형식, 인증 실패)는 전체 중단 + 보고서. 개별 항목 실패(키워드 하나 조회 실패)는 그 항목만 "보류"로 표시하고 계속
- AI가 추측한 정보를 사실처럼 쓰지 않음. 다음 모듈은 이전 모듈의 승인된 결과만 입력받음

## 6. 검증 기준
1. 웹 검색으로 최신 정보 확인, 공식 문서·요금표 우선
2. 정보마다 **[사실 / 추론 / 확인 필요]** 표시, 출처 URL, 확인 날짜(YYYY-MM-DD)
3. 홍보 문구만으로 성능 판단 금지. 무료 표시 서비스의 API 비용·제한 별도 확인
4. 없는 기능·API·가격·사례를 만들지 않음
5. "자동화할 수 있다"와 "수익이 난다"를 구분

## 7. 최종 보고서 형식
① 핵심 결론(5줄 이내): 발전 수준, 개인 개발 가능성, 무료 범위, 최대 제약, 다음에 만들 기능
② 현재 구현 검증: 2장 표의 각 항목에 대해 "맞음 / 수정 필요(근거) / 확인 필요"
③ 솔루션 비교표
④ 자동화 가능 범위표: 완전 자동 / 반자동 / 조건부 / 판단 불가 + 근거
⑤ 권장 아키텍처: 모듈 간 데이터 흐름 도식, 입출력, 승인 지점
⑥ 무료 기술 스택: 도구, 무료 조건, 제약
⑦ 개발 순서: 주 5~8시간 기준, 단계마다 실제로 작동하는 결과물과 검증 방법
⑧ 비용 분석: A 무료 직접 개발 / B 무료 + 일부 유료 / C 상용 솔루션 — 초기 비용, 월 유지비, 개발 시간, 유지보수 부담. **1장의 운영 규모와 시간 가치로 계산**하고, 확인 안 된 비용은 "추정"으로 표시
⑨ 최종 권고:
  1. 지금 직접 개발하는 것이 합리적인가?
  2. 기존 서비스가 더 유리한 부분은?
  3. 다음에 개발할 모듈은?
  4. 무료로 시작하려면 포기·축소할 기능은?
  5. 실제 판매·수익 검증에 필요한 최소 시스템은?

## 최종 원칙
AI를 많이 쓰는 시스템이 아니라, 최소 비용으로 실제 작동하고, 상품 선정 정확도를 높이고, 반복 업무를 줄이고, 수익성을 검증할 수 있는 시스템을 목표로 한다.

## 변경 이력 (v1 → v2)
1. **현재 구현 상태(2장) 추가**: 이미 만든 M1·M2를 다시 설계하지 않고 검증·보완하도록 함.
2. **운영 규모·시간 가치 입력칸 추가**: 비용 비교(⑧)와 "직접 개발이 합리적인가"(⑨-1)에 계산 근거가 생김.
3. **조사 우선순위 지정**: 9개 업무 × 여러 서비스를 한 번에 다 하면 얕아지므로, 다음 개발(M3~M5) 판단에 필요한 C·D·H를 1순위로 둠.
4. **H(정책·법규·데이터 이용 제약) 신설**: 네이버 API 데이터를 AI에 넣거나 저장해도 되는지, 자동 등록 제한, 등록 전 법적 요건.
5. **G(AI 쇼핑 에이전트 노출) 신설**: 2027년 AI 간 거래 대비라는 목표를 조사 항목으로 반영.
6. **현재 설정값 검증 요청**: 수수료율 등이 2026년 실제와 맞는지 확인.
7. **오류 처리 원칙 구체화**: 구조 오류는 전체 중단, 항목 실패는 보류 후 계속(현재 프로그램 방식과 일치).
8. **보고서에 "현재 구현 검증"(②) 추가**, 정보마다 사실/추론/확인 필요 표시와 확인 날짜 형식 지정.
