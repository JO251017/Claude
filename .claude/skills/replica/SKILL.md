# Replica — 분석 → 복제 → 개선 재구축

목표: 원본을 그대로 베끼는 것이 아니라, 원본의 구조·패턴을 정확히 추출한 뒤 약점을 보완한 **개선판**을 만든다.

## 0. 대상 유형 분류 (먼저 1개 선택)
| 유형 | 입력 | 기본 산출물 |
|---|---|---|
| A. 문서·보고서 양식 | docx/pptx/xlsx/pdf/이미지 | 원본과 같은 파일 형식 |
| B. 문체·말투 | 본인이 쓴 글 샘플 3개 이상 | 스타일 프로필 + 신규 초안 |
| C. 웹/UI 디자인 | URL·스크린샷 | HTML/CSS 또는 프레임워크 컴포넌트 |
| D. 앱 | 앱 설명·스크린샷·URL | 기능 명세서 + 동작하는 MVP 코드 |

유형이 불명확하거나 산출물 형식에 따라 결과가 크게 달라지면 질문 1개만 하고 멈춘다.

## 1. 분석 — 원본 스펙 추출
원본을 끝까지 읽고 아래를 표로 정리한다. 추정한 항목은 "추정"으로 표기한다.
- A 문서: 섹션 구조, 제목 위계, 표·차트 형식, 폰트·색·여백, 문장 길이·어미, 고정 문구 vs 가변 내용
- B 문체: 어미·존댓말 수준, 문장 길이, 자주 쓰는 표현·접속사, 구조 습관(두괄식 등), 피하는 표현
- C UI: 레이아웃 그리드, 컴포넌트 목록, 색·타이포 토큰, 간격, 인터랙션, 정보 위계
- D 앱: 핵심 사용자 흐름, 기능 목록(필수/부가), 데이터 모델, 화면 목록, 수익 구조(해당 시)

## 2. 진단 — 원본의 약점
MECE로 3~5개만 뽑고, 각 항목에 근거를 단다.
- 가독성 / 정보 밀도 / 중복 / 사용성 / 누락 기능 / 일관성 / 접근성 / 자동화 가능 지점

## 3. 개선 설계
| 약점 | 개선안 | 기대 효과 | 난이도 |
원본의 핵심 의도·사실은 바꾸지 않는다. 사용자가 원하지 않으면 개선은 최소 범위로 한다.

## 4. 재구축
- 사용자가 준 새 내용(또는 지정 주제)으로 산출물을 만든다.
- 문서 양식은 원본 파일을 템플릿으로 복사해 내용만 교체하는 방식을 우선한다(서식 손실 방지). python-docx / python-pptx / openpyxl 사용.
- 웹/UI는 디자인 토큰을 CSS 변수로 먼저 정의한 뒤 컴포넌트를 만든다.
- 앱은 MVP 범위(핵심 흐름 1개)부터 동작하는 코드로 만들고, 실행·테스트까지 확인한다.

## 5. 검증
- 원본 대비 스펙 일치 체크리스트(구조·서식·톤) 통과 여부
- 개선 항목이 실제 반영됐는지 확인
- 파일은 열어서, 페이지는 렌더링해서, 코드는 실행해서 확인

## 출력 형식
1. 산출물 (파일 경로)
2. 원본 스펙 요약 (5줄 이내)
3. 적용한 개선 사항 (3줄 이내)
4. 결론이 틀릴 수 있는 조건 1개 (예: 원본 샘플 부족)

## 경계 (반드시 준수)
- 사용자 본인 또는 사용자 회사 소유 문서·양식은 자유롭게 복제한다.
- 타사 웹/앱은 **구조·기능·UX 패턴**만 참고하고, 상표·로고·브랜드명·고유 일러스트·문구·코드는 가져오지 않는다. 시각 정체성은 새로 만든다.
- 실제 서비스로 오인될 수 있는 결과물(로그인·결제 화면 모사, 공식 기관 사칭 페이지)은 만들지 않는다.
- 문체 복제는 사용자 본인 글 또는 당사자 동의가 있는 경우에만 한다. 타인 사칭용 글은 작성하지 않는다.
- 저작권 있는 원문(기사·책·가사 등)을 그대로 옮기지 않는다. 양식과 구조만 복제한다.
